# 作者修改要求的验收闭环

## 已复现的问题

2026-10-17 检查本地运行记录确认：作者输入“中间撕了一张怎么会隔一页呢？”已进入 planned_writer 的 rewrite.instruction。生成的新稿仍保留“十七到十九缺一页、抽走一张”的表述；两路评审均返回空 findings。修改要求没有进入一致性评审输入，因而此前的“无问题”不代表完成了作者要求。

本段与后段还共享同一页码表述。邻段只读是写入边界，不是要求作者保留错误的事实依据。涉及编号方式不明、必须联动邻段时应交作者决定，不能悄悄改邻稿或虚构编号设定。

## 实现

- 保留同一 planned_writer 作者角色和现有 Writer → 双评审 → 人工门禁编排。作者反问按编辑要求理解，提示词升级 planned_writer.v6。
- 一致性评审接收作者原要求、修改前原文及当前稿，附带原有冻结前后文；不接收 Writer 的自我解释作为通过依据。
- 有作者要求时，在同一次 hard_consistency 调用中强制返回 authorCheck：addressed / unresolved / needs_clarification、理由、当前目标正文引文。对应提示词 hard_consistency.v6、契约 hard_consistency.revision.v1。演示 ch7 的工具查证路径保留独立查证，再做此项验收；真实规划写作不增加调用数。
- 程序验证字段、状态、引文与版本；缺失验收、无效引文不能按空结果放行。未解决/需澄清会形成 requiresHuman 问题，阻止批准。完全不变的替换正文不会保存为新稿。
- ChapterState.authorRequest 保存当前人工要求，checkpoint 和操作幂等产物携带它。更新上下文的纯复检通过 ContextBundle.revisionRequest 携带旧要求，固定在输入摘要中，但不会重新执行 Writer；切到另一情节段不继承不属于它的要求。
- 旧记录缺少针对性验收时显示“尚未核对修改要求”，不伪造通过结果。继续修改或复检后才生成新验收。

## 界面

正文旁右栏使用单一滚动区：当前稿、已提交要求和结果、修改表单、确认动作、折叠历史与高级选项。取消底部固定的大块确认区。表单明确修改范围、未发送状态及字数限制；发送是主操作。批准后才显示事实确认及采用操作，保留两步业务门禁。

## 验证与边界

自动化用例覆盖：反问型要求传给复检、空 findings 不足以放行、虚构引文被拒、原文未变被拒、未解决/需澄清阻止批准、checkpoint 保存要求、更新上下文复检保留要求且不重写、不同情节段不串要求，以及前端旧记录/当前验收/运行状态展示。

这保证了验收材料和程序门禁，不能保证模型每次语义判断都正确。工程回归使用 Fake 和隔离数据库。随后已完成隔离合成样本的真实模型验收，最终八样本通过；仅作者重写及其针对性复检启用推理，并保留先前失败记录。见[真实验收报告](evaluations/2026-10-17-author-revision-live.md)。历史正文和采用记录保持原样；真实作品当前页码与邻段处理仍需作者核对。
