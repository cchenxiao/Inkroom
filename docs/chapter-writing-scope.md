# 整章生成与局部重写设计

状态：2026-10-17 实现；沿用现有 Eino 编排与 PostgreSQL 持久化。

## 业务规则

- 默认主入口生成整章，一次作者模型调用返回按细纲排序的情节段。保留「生成本段」，不要求逐段人工开工。
- 整章、单段、选区重写均使用 `planned_writer` 作者角色。两路审稿负责提意见；原有自动修订角色仍仅修复授权范围内的问题。
- 作者可在没有审稿问题时主动重写。指定选区只允许替换该范围；范围外文字由程序保留，不依赖提示词承诺。
- 生成与修改产物都是候选；重新审查后等待作者判断。批准、采用候选、组稿、整章复审、最终定稿保持独立。
- 已采用稿不可变，修改已采用稿另建候选，不直接覆盖历史。

## 入口与编排

| 操作 | 输入范围 | 接回现有编排的位置 | 输出 |
| --- | --- | --- | --- |
| 生成整章 | 确认细纲的全部情节段及各自人物知识、视角、时间、文风 | `draft → critics → aggregate → human_gate` | 全部段落的一个候选版本 |
| 生成本段 | 本段任务与前后最新保存正文（包括未采用稿） | 同上 | 单段候选 |
| 待审核候选的选区修改 | 当前稿版本、完整原文、Unicode 范围、作者要求 | `human_gate → apply → recheck → human_gate` | 新稿版本，仅选区文字改变 |
| 已采用、旧版本或旧格式候选的修改 | 来源运行及版本、本段原文、新冻结上下文 | 新运行的 `draft → critics → human_gate` | 保留历史的新候选 |
| 上下文过期后复检 | 当前选择的本段原文、新冻结上下文 | `draft` 原样传递正文 → 双路审稿 → 人工门禁 | 正文不变的新候选 |

`mode=chapter` 使用独立的整章候选稿本，单段仍用原有稿本 ID。整章结果保留真实 `beatId` / `sceneId` / POV；组稿按 `beatId` 提取，不能把整章重复填入每一段。

## 冻结材料

每个任务沿用 `PreparePlannedContext` 和已发布知识快照；整章 `targets[]` 的每一项分别经过 POV/故事时间投影。后段的已知事实不能作为前段角色的知识。

单段任务自动读取细纲相邻两段最新保存的工作稿，包括未采用候选和作者已保存的修改；按该情节段最后一次正文实际变化的时间选择当前稿本头（不是整个稿本最后保存时间），固定来源运行、稿本版本、校验值和段名，放入 `neighbors[]`。只有没有任何已保存正文时才标记为空。不读取未完成的流式片段或浏览器未保存修改；未采用稿标记为 `candidate`，不把它当作已确认事实。页面未选中的邻段使用同一工作稿来源。邻段属于只读叙事参照，用于动作、位置、物件状态、语气和重复描写检查；后文不能提前转成角色已知事实。

本次使用完整相邻情节段，不自动生成摘要、不静默截断。超出材料预算则停止。更远前文的压缩摘要、作者手动指定历史邻稿，以及后续章节定稿交接不在本次实现范围。

作者修改参数为 `segmentId + original + start + end + instruction`。`start/end` 是 Unicode 码点偏移，结束位置不包含；服务端验证完整原文和稿本版本。页面遇到重复短引文要求扩大选区，避免修改错误位置。模型只返回替换文本，服务端拼接前后缀。

系统提示词版本由 `internal/agents/prompts/prompts.go` 固定，并记录在每次调用元数据中。单段与选区返回 `{text}`，整章返回 `{parts:[{beatId,text}]}`。校验失败、截断或缺段不会保存为成功稿件。整章必须按细纲顺序返回全部段落，不能缺失、重复或自行新增。

## 审稿与版本门禁

- 一致性审稿读取目标正文、分段知识投影和固定邻段；语言审稿读取正文、风格指标及邻段。二者不互看对方结论。
- 整章一致性问题按所属段校验事实引用，不允许借用另一段才知道的事实作为当前段的确认依据。
- 所有写入、批准、采用沿用乐观版本锁与幂等请求 ID；Eino 人工 checkpoint、操作回执和重试缓存继续使用原有机制。
- 新任务固定目标段当前采用版本作为 `baseline`；单段任务还固定邻段工作稿版本。批准、保存 checkpoint 和采用时在规划锁内重新比较目标 baseline、规划和知识；邻段变化独立提示。整章与单段交错操作不能覆盖更新的采用稿。
- 本段采用基线、规划或知识变化仍使旧候选审核失效。邻段正文/视角变化仅标记 `neighborsChanged`，不阻止本段审核与采用；作者可自选复检，跨段衔接由冻结组稿后的整章复审统一核对。冻结上下文不回写。已发现硬伤、未完成检查、未确认修改等原有门禁不变。已采用历史保留原审批记录。
- 新采用稿替代组稿来源后，旧组稿选择失效，需要重新组稿和整章复审。只改变未采用候选不代表已经替换正式采用稿。

## 页面行为

- 空白章节主按钮为「生成整章」；审核面板的「生成范围与自动修订」保留整章和单段入口。
- 正文右键/选区操作绑定段落 ID 与版本，修改要求直接进入作者重写；已采用稿建立新候选。
- 整章候选明确展示审批范围，并使用「批准整章候选」「采用整章候选」，避免误解为只审批当前选中的一段。
- 单段候选展示前后段名称、引用版本及「未采用工作稿／采用稿」状态；过期候选可「保留本段正文，按最新上下文复检」。技术编号保留在排查详情中。

## 预算与限制

默认材料预算 32768，单次输出预留 8192，运行预算上限 128000，调用数上限 14；环境变量显式配置优先。预算仍按 UTF-8 字节保守预估，实际 token 以供应商回执为准，预算上限不代表实际消费。增加容量是为了容纳整章分段任务与相邻正文，不启用任何自动付费试跑。

当前沿用首章门禁，整章支持 1–8 个细纲情节段。长章超预算会停止，不声称支持无限长度一次生成。模型对事实和衔接的语义检查仍可能漏报，作者审核不能省略。

## 验收

- 单次作者调用完整输出有序段落，拒绝错序、重复、缺段。
- 中文与 emoji 选区定位正确，选区外及其他段落逐字不变，无问题候选也可主动重写。
- 数据库集成验证：整章生成、人工 checkpoint 恢复、选区改稿复检、幂等重试、批准采用、按段组稿及整章审稿输入。
- 邻段变化提示衔接待整章核对，不循环阻止各段审批。组稿逐段比较最新工作正文与采用稿，忽略纯稿件版本变化；本段真实改动仍必须采用新候选，旧整章来源不能绕过新的单段采用稿。
- 前端全套测试、lint、build，Go 测试及数据库/编排 race 检查。测试使用 Fake 模型和独立数据库，不修改真实作品或调用付费模型。

历史冻结上下文不重写。旧规则的单段候选在作者下一次修改时另建运行，使用新的工作稿引用规则。

## 三段工作稿回归（2026-10-17）

整章稿本和单段稿本共存时，保存第三段会更新整章保存时间，但不能让其中未改动的第一段压过独立稿本中较新的第一段。`workingPassage` 现在比较每个稿本内该 Beat 的正文变化历史（忽略稿本/段版本号、稿本 ID 和 order 等元数据），按实际叙事变化时间排序；返回的来源仍是选中稿本的完整当前版本，以便追溯。

数据库测试覆盖：三段整章生成 → 第一段单独保存未采用稿 → 中间段冻结左右最新工作稿 → 修改第三段 → 中间段保持可批准并提示衔接待核对 → 可选原文复检引用新第三段，同时仍引用独立修改的第一段。冻结历史不回写。查询沿用现有历史和主键索引，无数据迁移；大规模版本历史的性能尚需后续测量。

正常篇幅真实模型验收使用 `go run ./cmd/inkloom -chapter-workflow-eval`，仅在内存中复用生产编排，真实模型调用但不写作品数据库。报告保存原稿、前后候选、改稿、双路评审、调用版本和用量；先核对整章顺序与篇幅，再检查中间段修改和四字选区范围。真实选稿和失效行为由上述独立数据库测试验证，不能把内存构造的邻稿当成数据库链路验收。详情见 [整章验收报告](evaluations/2026-10-17-chapter-workflow-live.md)。


## 2026-10-17 篇幅提示与实验衔接检查

每次本版复检保存程序统计的实际篇幅与单段/全章目标，右栏轻量展示。按非空白字符含标点计数；75%–133% 是提示范围，不是强制删改或作者批准门槛。旧版本、失效来源和未保存编辑不复用该提示。

新逐段衔接核对仅在 `INKLOOM_EXPERIMENTAL_CONTINUITY=true` 时进入冻结的 WritingTask；默认 false。复用一致性评审角色和总预算，逐段附带对应 POV 事实及相邻只读正文，校验引文、状态与意见。长期篇幅实验仍有漏检/截断，详见[验收报告](evaluations/2026-10-17-continuity-quality.md)，不默认开启。旧冻结任务不随环境开关变化。

## 审核未完成与保留正文复检（2026-10-17，第三轮）

审核失败通过 `criticReviews[].failureCode` 向前端提供稳定原因。右栏显示“检查未完成”，保留稿件，作者可显式重新检查本段或整章。整章请求为 `mode=chapter, recheck=true, fromRunId, sourceVersion`，禁止携带 rewrite 或启用 autoRevise，来源版本必须等于当前章稿版本，所有情节段与场景必须与当前细纲一致。新运行复制原文并跳过 Writer，保留原作者要求，重新走审核和人工门禁；不自动采用结果。

实验长文检查完整保留前后文，按物件/人物两类任务核对，任一失败整体不报通过。已移除模型填写冗余目标编号的要求，由程序依据两处证据定位授权段。真实模型仍有推理截断或普通模式漏检/误报，默认开关保持关闭。参见[本轮记录](evaluations/2026-10-17-review-recovery.md)。

### 2026-10-17 作者确认的正常篇幅

本次作者明确希望正常章节在 2000–3000 字左右。正常整章评测以 2400 为目标，验收收紧至 2000–3000 个非空白字符；约 4200 字的旧失败稿仅保留作衔接压力回归，不作为正常篇幅通过样本。新增约 2050 字的固定衔接正反对照与 30000 输出额度实测，见 [审核恢复记录](evaluations/2026-10-17-review-recovery.md)。此变更先落在验收工具与创作要求中，不静默修改已保存的作品细纲；Writer 稳定控制篇幅的生产验收仍待完成。


### 作者可选的加强衔接检查与工作台布局（2026-10-17）

新增请求字段 `enhancedContinuity`，省略为 false。规划写作请求显式选择覆盖环境变量，冻结到 WritingTask 与运行来源；整章组稿复审冻结到 input 与摘要。同一 requestId 改变选择视为幂等冲突，已开始的运行、历史稿和已发送请求不随开关变化。

工作台工具栏只有一个「检查设置」入口，单段生成、整章生成、新建复检和组稿复审共用本次工作台的选择，刷新或切换章节后默认关闭。右侧两页不重复摆开关：审核本段按当前状态→检查与改稿回执→修改要求→批准/采用排列；检查明细和候选历史折叠，保留正文复检归入明细，失败和来源变化时才在当前步骤突出复检。整章页按整理章稿、复审、定稿顺序展示，历史记录折叠。独立旧版复审组件没有工作台时保留折叠的本地设置。

修改要求仍先走 Writer/改写，再走基础事实一致性与语言审核；新开关只控制额外的叙事状态核对。已有任务内的修改沿用原冻结选择，需应用新选择时显式创建「保留正文，重新检查」。试用发现统一 requiresHuman，不触发自动改写；检查失败不当作通过，正文不变。

本轮同时修复选中审查意见后，轮询产生新 findings 数组反复 scrollIntoView 的回跳；定位只依赖选中意见及其实际目标。段落重新生成去除重复确认弹窗，旧稿保留，新请求直接进入审核面板，失败提示紧邻当前稿状态。前后端须一并更新，旧后端的严格解码会拒绝新请求字段。

### 正文问题的就近处理（2026-10-17）

问题卡片按引用原文定位到自然段下方。卡片是编辑器装饰，不进入正文保存、导出或撤销历史；轮询不触发重复滚动。引用失效或重复时不猜测修改位置。

卡片内提供三个明确动作：

- **我来修改**：展开引用原文编辑框，以 `inline_edit` 仅替换这处文字，保存后沿用现有双评审流程；已采用稿先建立新候选。前后文与其他段落不变。
- **让模型修改**：携带该问题的原因、作者要求和原文，可选仅引用或当前情节段。使用现有 `rewrite` / 版本化新运行入口，不再误用旧 `instruct` 的自动修复门禁。跨段意见不会自动扩大授权到邻稿。
- **保留原文**：点击即提交 `finding_decision`，无需填写理由或二次确认；提供“撤销保留”。记录问题 ID、稿本版本、keep/reopen，理由可为空（兼容历史理由）。复用人审编排 apply → human_gate、事务产物与 checkpoint，不调用 Writer/Critic、不新增正文版本。判断持久化到运行并保留操作历史，可恢复待处理；新版正文不继承旧判断。P3 待作者判断项可据此完成裁定，P0–P2 硬性阻断及未完成的作者要求核对仍不可绕过。批准与采用仍由作者分别执行。

验证包含引用替换范围（含 Unicode）、歧义拒绝、模型请求内容、失败保留输入、明暗主题卡片操作、保留/恢复、数据库重连与幂等、批准/采用及版本保护。真实稿件未用于写入测试。

### P3 逐条处理与统一复审（2026-10-17，修正）

P3 问题卡片改走局部处理，不再每改一句就调用两个 Critic、重建全部问题列表：

1. `propose_finding` 固定问题 ID、稿本版本与唯一引用范围，只调用 Writer。结果存为 `findingProposal`；正文与版本不变，作者就地查看前后对照，可确认或放弃。引用外的标点不变，模型返回与边界重复的单个标点会从替换文本中移除；省略号、破折号不做这种归一化。
2. `apply_finding` 校验预览 ID/版本/原文后保存替换。作者直接修改对应 `edit_finding`。每次实际写入递增稿本版本，保留旧报告与原问题编号作为工作清单，记录 `findingChanges` 并设置 `reviewPending`，不调用完整评审。原引用已变化或出现多处时拒绝猜测位置。
3. 作者可连续处理其余问题。已修改项标记“待统一复审”，不宣称已经解决；保留原文仅是作者判断。`review_batch` 由作者显式触发，对最新稿执行必要双评审，成功后更新报告并清除待复审标记。新报告可能复用问题编号，旧的保留判断只留在操作/产物历史，不自动应用到新报告。没有最新完整评审、或仍有未确认预览时，服务端禁止批准/采用。

这些操作继续通过现有人审图与事务产物/checkpoint 恢复。保存预览、放弃预览不新增正文版本；确认与重复请求不会重复写入；预览产物已保存但 checkpoint 失败时不会再次调用 Writer。普通整段重写及非 P3 处理仍使用原有完整复检链路。局部预览只校验范围、拼接与输出结构，语义质量由作者对照确认，并由统一复审检查，不显示为“审核通过”。

新增验收覆盖三个 P3 的连续处理、未确认预览的正文不变、放弃/恢复、批量复审前禁止批准、实际数据库重连与故障恢复、标点与 Unicode 边界，以及明暗主题下的原文旁预览。测试未修改真实作品正文。

### 2026-10-18：采用与衔接复审分离
