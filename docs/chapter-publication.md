# M0.4c5a 整章定稿与事实边界

入口：真实章节写作 → 组稿与复审 → 作者确认复审通过 → 整章定稿。

## 作者操作

1. 通读章稿和复审意见，确认复审通过。
2. 核对是否存在需要同步的新增事实或设定冲突。只有明确选择“没有待同步事实”才能定稿；选择有待处理内容时保留章稿并阻断。
3. 点击“确认整章定稿”。成功后显示独立定稿版本、对应章稿版本、时间和回执 ID。刷新页面仍可读取。
4. 正文、规划、知识或复审批次发生变化后，原定稿成为历史记录；其正文和作者确认不会被改写。新版本仍需重新组稿、复审和定稿。

**本步没有自动事实抽取，也没有事实写回。** 作者确认是目前的人工边界，不是模型已核对全部事实的证明。有新增事实时不能靠勾选跳过；下一步单独实现带正文证据的事实候选与逐条确认，再做下一章前情交接。台词、角色误解、规划中的未来事件都不会自动进入知识库。

## Go 实现与 Agent 边界

定稿不是一个新 Agent：它是作者授权后的确定性数据库事务。继续复用上一阶段两路 Critic 的完整审查结果，不重新调用模型，也不通过自动重试争取“审到通过”。

- `app.ChapterPublication` 区分整章定稿与单 Beat 的 `FinalCommit`。前者冻结章稿、两路审查、模型调用记录、作者批准与事实声明；章稿的每个 part 保留其 Beat commit 和来源，知识版本沿用不可变引用。
- `postgres.PublishChapter` 按规划 → 知识 → 稿本的固定锁顺序重新核对当前来源、最新章稿和最新复审批次。两个 Critic 完整完成、无阻断项且作者批准之后才可写入。
- 请求携带 `assemblyVersion`、审读 `inputDigest`、`approvalId`，作者确认只对这个版本有效。新版本或新审批不能复用旧确认。
- 迁移 018 创建 `chapter_publications`。同一复审批次只允许一份定稿，同一章按版本追加，保存上一份定稿 ID；不修改组稿、单段提交或知识头。
- 同一 `requestId` 与完全相同内容重试返回原回执；同 ID 改内容、对同批次重复新建返回 409。原请求成功后即使来源变更，仍返回原回执，另附 `current:false`，不重新批准旧稿。
- `current` 每次读取推导。历史定稿可追溯，但不能被后续章节当作当前有效来源；下一章接口仍未开放。

## 接口

Go 前缀 `/api`，前端代理 `/go-api`；Mock 契约不变。

| 方法 | 路径 | 请求 / 返回 |
| --- | --- | --- |
| POST | `/planning/chapter-publications` | `{requestId,reviewId,assemblyVersion,inputDigest,approvalId,noPendingFacts}` → 定稿状态 |
| GET | `/planning/chapter-reviews/:id/publication` | 对应复审批次的 `{publication:null或冻结记录,current,reason}` |

缺少作者事实确认、门禁不满足、版本变化或幂等内容不一致返回 409，未知复审批次返回 404，暂时不可用返回 503。

## 前端与恢复

`ChapterPublication` 复用 API client、TanStack Query、按钮和 pending 编辑保护。提交结果未知时保留完整请求，只允许原请求重试；轮询读到同 ID 回执也能恢复。409 清除本次事实选择并禁用旧版本提交。其他标签存在未保存编辑或未知写请求时也不能定稿。

历史章稿和复审批次在查看期间固定，不因另一窗口新建批次而卸载正在操作的表单。退出工作台仍走已有未保存内容提示。

## 验证范围

使用专用 PostgreSQL 与 Fake，不调用付费模型、不向生产库写测试作品。关键回归覆盖事实未确认、作者未批准、错误版本/批准 ID、并发同请求去重、重试内容不一致、历史回执与旧版本失效；前端覆盖确认门禁、503 原请求重试、409 置灰和刷新读取定稿。
