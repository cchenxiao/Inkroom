# 墨枢 Inkloom · 后端增量开发与 Agent 技术学习计划

> 这份文档有两条线拧在一起：
> - **明线（创作编排）**：系统从"能写一段"一点点长成"能自动写完并守护一章、再到跨整本书"。
> - **暗线（你要学的 Agent 技术）**：每写一刀代码，就扎扎实实练到一项可写进简历、能扛面试追问的 Agent 工程技术。
>
> 配套：静态结构见 [backend-architecture.md](./backend-architecture.md)；流程与角色见 [agent-orchestration.md](./agent-orchestration.md)；接口字段见 [frontend-api.md](./frontend-api.md)。
>
> 方法论：**评测驱动的垂直薄切片**——每一刀都端到端可跑、可测、可演示，只在被真实失败逼到时才加一个节点/工具/护栏。先窄后宽，先能跑后变好，先 Fake 后真实，先单章后跨章。

> **当前学习执行约定**：按作者要求，前期不强制先写测试或铺全量用例；I0–I3 通过 `go build`、`go vet` 和 Fake 驱动的 CLI 场景验证。下文的测试场景作为验收目标，涉及持久化、并发与恢复时再逐步固化关键回归。当前已推进至 I8：增加同事务事件/outbox、SSE 断线重放、消费去重与真实流程图，准备页已取消轮询。I7 在 PostgreSQL 乐观并发之上增加 Eino 人审检查点、approve/instruct/inline_edit、稳定操作 ID 与事务内产物去重；恢复不会重跑 Writer，模型预算跨恢复累计。I4 补三组边界测试，I5/I6/I7 各补一组关键测试；按增量边写边解释，不一次推进全部里程碑。

## 2. 五条建设原则（也是 Agent 工程的正确姿势）

1. **竖着切，不要横着铺**：每刀都是"喂一个 beat → 过若干节点 → 产出可断言结果"的完整链路；DB、HTTP、SSE 在真正需要那一刀才引入。
2. **Fake LLM 是默认开发驱动器**：定 `ChatModel` 端口，测试/CI 全用脚本化 Fake（正常/坏 JSON/截断/非法引用/拒答/二次修复成功）。真实模型只在开发机手动跑、按种子集跑，**CI 不依赖真实 LLM**。这样编排/校验/路由从第一天就确定可测，还不花钱。
3. **先有失败用例，再加能力**：先写 1–3 条"现在过不了"的用例（红）→ 最简实现变绿 → 换真模型看真实失败 → 判断缺口属于 提示词/校验/工具/上下文/路由/护栏 哪一类 → 一次只加一类 → 全量回归。**没有失败案例支撑的节点不许进图。**
4. **能假先假**：内存→PG、固定上下文→检索、单模型→路由、同步→worker、无鉴权→鉴权。interface 先定、适配器后换。
5. **依赖顺序不能反**：上下文与版本契约先于并行评审和人工审批，授权判断先于修订执行，可见性过滤先于检索与工具，事件先于流式，持久化先于续跑。基础设施可以延后，这些正确性约束不能延后。

### 每个增量的标准循环

```
① 写失败用例（domain 单测或 eval 种子），先跑红
② 最简实现（内存仓库 + Fake 模型）变绿，不提前抽象
③ I3 起按需换真实模型跑固定种子；先记本地结构化调用记录，I6 落库，I20 接 Langfuse
④ 看真实失败，归类到：提示词 / 输出校验 / 工具 / 上下文 / 路由 / 护栏
⑤ 只加一类复杂度，重跑
⑥ 全量回归 + 提交（旧用例全绿，记录 eval 数据与 prompt 版本）
```

完成定义（DoD）：自动化用例全绿（CI 用 Fake）；有一条能给人看的演示；关键决策与 prompt 版本有记录；I3 完成最小前后端联通，I8 补可靠流式；不新增 flaky 测试。评分从首次出现就区分已校准门禁与未校准提示，不能等到 M4 才限制未校准项。

## 3. 第一周从哪行代码开始（I0–I1）

**先不碰数据库、不碰真实模型。**

1. `cmd/inkloom` + `internal/config`：能启动、读配置。
2. `internal/domain/manuscript`：`Segment`、`Beat`；`internal/domain/review`：`Finding`、severity(P0–P3)、`ReviewReport`。
3. 纯规则单测立标杆：聚合分级（去重、P0 优先）、Finding 引用校验——**第一批红→绿**。
4. `internal/agents/model` 定端口 + `FakeChatModel`（按脚本队列返回多轮预设响应）：
   ```go
   type ChatModel interface {
       Generate(ctx context.Context, in ModelInput) (ModelOutput, Usage, error)
   }
   ```
5. `internal/orchestration` 用 Eino 搭 **3 节点最小图**（writer → 一个 critic → 结束），状态放内存 struct，输入用最小 `ContextBundle`（Beat、基础设定、来源版本）；图测试：喂 1 个 beat，断言产出 segment、且 Fake 给的 P2 finding 被解析进 ReviewReport。

目的：用最便宜、最确定的方式把 **"图—状态—结构化解析—评审结果"** 主轴钉死，后面所有能力往里挂。

## 4. M1 学习卡（当前阶段，I0–I9，逐刀详写）

> 每张卡：**学什么 Agent 技术 / 对应 Go 技术 / 你要写的代码 / 创作上发生什么 / 学会的标志 / 能讲的一句话**。

### I0 · 工程骨架与领域模型
- **Go 技术**：接口隐式实现、结构体与枚举、错误包装、表驱动测试。
- **技术**：端口/适配器（六边形）雏形、Go 领域建模、TDD。这一步还不"智能"，但决定了后面模型能否被干净替换。
- **写代码**：config；`Segment/Beat/Finding/Severity/ReviewReport`；聚合分级与 Finding 校验纯函数；`ChatModel` 接口 + Fake。
- **创作上**：系统能表达"一段正文"和"一条带级别的问题"。
- **学会的标志**：不依赖任何网络，`go test ./...` 绿；新增一个假模型实现不用改业务代码。
- **能讲的一句**："我把 LLM 抽象成端口，编排逻辑对 Fake 和真实模型一视同仁，所以 CI 全离线、可复现。"

### I1 · 行走骨架：第一张图
- **Go 技术**：包依赖与组合、值和指针语义、输入快照与状态更新。
- **技术（核心）**：**Graph + 共享 State、节点(node)与边(edge)、图编排 vs 自由群聊**。
- **写代码**：Eino 3 节点图，节点只做"取状态→调模型/服务→写增量"，业务规则不进节点；内存 `ChapterState` 与最小 `ContextBundle`。基础设定按版本引用，正文产物独立编号；此时只需固定材料，不引入检索或数据库。
- **创作上**：beat 进 → writer 写一段 → critic 评一条 → 结束，端到端打通。
- **学会的标志**：能讲清状态怎么在节点间流动、为什么节点要薄、为什么不做 AutoGen 式自由群聊（可控/可测/防失控）。
- **能讲的一句**："我用显式状态图而不是让 agent 互相呼叫——路由权在图和护栏手里，模型只在节点内做判断。"

### I2 · 结构化输出加固
- **Go 技术**：encoding/json、错误分类、引用与边界校验。
- **技术（核心）**：**让非确定性模型产出可被程序依赖的结构**——schema 约束、解析管线（结构→字段→枚举→引用存在性→修改范围）、最多一次 JSON 自修复、拒答/截断/空响应分支。
- **写代码**：`parse` 包 + 五类异常的 Fake 脚本与测试；非法引用（quote 在正文里找不到）直接判无效。
- **创作上**：Critic 报的问题从此带得准定位（哪段、引用哪句、为什么、建议怎么改）。
- **学会的标志**：能解释"有效 JSON ≠ 有效证据"；五类异常各有测试，绝不把解析失败当"审稿通过"。
- **能讲的一句**："模型输出我做了四层校验，引用必须在正文里真实存在，解析失败是节点失败而不是放行。"

### I3 · 接真实模型 + Prompt 四段式
- **Go 技术**：context 超时/取消、HTTP client、错误分类与有限重试。
- **技术**：**模型适配层、Prompt 工程、token/用量记账、prompt 版本化**。
- **写代码**：Eino ChatModel 真实适配器（先一个供应商）；writer/critic 的四段 prompt（职责与边界 / 输出 Schema / 任务要求 / 故事材料）；本地结构化记录 usage、prompt 版本与调用结果，I6 再落 `llm_calls`。加入调用超时、取消、有限重试及 run 总调用/token 预算；修复和重试均计入，未知费用不能记为零。
- **创作上**：第一次用真模型写出一段像样的正文和一份像样的评审。
- **最小联通**：内存仓库提供 `POST /runs` 与 `GET /runs/:id`，前端轮询查看运行结果；保留现有契约，未实现资源仍由 Mock 提供。此时不建设可靠 SSE，I8 再替换轮询。
- **学会的标志**：改一个环境变量就能在 Fake/真实间切换；会把真实失败归类（是 prompt 没说清，还是校验/上下文问题），而不是无脑重写 prompt；测试超时、取消与预算耗尽后不再发起模型调用。
- **能讲的一句**："Prompt 我按职责/Schema/任务/材料四段组织并版本化，正文里出现的指令句只当故事材料，防注入。"

### I4 · 评审-返工闭环（先做 P2 / 去 AI 味）⭐反思循环
- **Go 技术**：显式状态机、循环终止条件、可注入时钟与预算计数。
- **技术（核心）**：**Reflection 自纠错闭环、条件循环、有限轮次护栏、escalate 终止、确定性文本特征**。
- **写代码**：ai_taste 的确定性特征（禁用词命中、句长方差/burstiness）；micro-polisher 只改命中句出 diff；修订生成新 draftVersion，critic 复检该版本；默认最多 2 轮修订，可配 3。初次评审不计修订轮数，同轮多个修订步骤不各算一轮，修复 JSON 的调用只计调用预算。
- **创作上**：稿里的"一股难以言喻的""嘴角勾起"被自动抓、自动微改、自动复检，在作者授权的句级范围内自动处理，超出范围先交人。
- **学会的标志**：能画出 revise→re-critic 的回边；能用测试证明"改后禁用词消失且指定回归用例通过""第 2 轮复检仍失败便 escalate，不启动第 3 轮修订"。
- **能讲的一句**："自我反思我做成有界循环：每轮复检修订后的版本；轮次上限与调用预算共同限制执行，到达上限仍未通过便升级人工。"

### I5 · 一致性 Critic 与分级路由 ⭐多智能体分工
- **Go 技术**：goroutine、errgroup/信号量、同步与 go test -race；并发 Fake 按角色/请求匹配响应，避免共享队列导致不确定测试。
- **技术（核心）**：**多专家 Critic 并行 + barrier 聚合 + 条件边路由 + 不同修订粒度**。
- **写代码**：hard_consistency critic 读最小 Bible（硬特质/knows）；structural / scene reviser；按 severity 选修复范围，再按授权判定是否执行；增加 `needs_human` 终态（此时无需持久化恢复）。并行节点只返回独立评审结果，由聚合器统一合并，避免并发写共享状态。
- **版本前提**：run 的 Bible/大纲/风格等基础输入版本固定；正文随修订产生新版本，同轮 Critic 读同一正文快照。人工更新使旧候选与审批失效，不把最新版本号补到旧结果上继续提交。
- **创作上**：P0 定位 Beat 级修复，P1 定位场景，P2 定位命中句；修改锁定大纲、重大结构、跨章或裁决事实冲突必须先出方案交作者。章内且已授权的局部修复才能自动执行。"左撇子"不等于"不能右手持刀"，证据不足只列待核实；硬冲突测试须提供明确约束（如右手受伤无法握刀）。
- **学会的标志**：分支测试覆盖 P0→beat、P1→scene、P2→micro，以及越权→needs_human 且正文未变；能说清"多 critic 不是投票，必要 critic 缺席不能被别人的通过替代"。
- **能讲的一句**："我让多个专职评审并行冷读同一冻结版本，聚合器按证据和严重度做确定性路由，而不是把分数投个票。"

### I6 · Postgres 持久化与版本
- **Go 技术**：database/sql 或 pgx、事务边界、条件 UPDATE 与受影响行数、迁移。
- **技术（生产化）**：**Agent 状态外置、版本化草稿、乐观并发控制**。
- **写代码**：migrations（segments/findings/runs 等最小集）；repository 换掉内存实现；正文写入按 chapter/branch 的期望 draftVersion 校验并递增，segment 保留自身历史版本，旧 patch/审批也校验其原始版本，冲突返 409；真实 PG 集成测试（本机独立测试库；CI 再按需接 testcontainers）。
- **当前实现边界**：`pgx/v5` + 内嵌迁移，章/分支版本头、正文快照、段版本、评审、运行与调用元数据；保留单段候选演示。重启只标记 interrupted/unknown，不自动恢复执行；审批入口与 checkpoint 留给 I7。
- **创作上**：重启稿子还在；两个窗口/人与 agent 同时改不会静默互相覆盖。
- **学会的标志**：杀掉进程数据不丢；能写出版本竞争返回 409 的集成测试。
- **能讲的一句**："所有写操作带 draft_version 做乐观锁，旧审批撞上新人修改直接失效。"

### I7 · 人在环：Interrupt / Checkpoint / Resume ⭐HITL
- **当前切片**：自动创作图之后接独立 HumanGate 图；单门禁采用 Eino implicit resume。指令只修已有局部问题，直改后双 Critic 复检，批准仅确认候选；不提前做事实传播、正式 commit 或可靠 SSE。等待检查点与人工操作恢复已落地；初稿阶段任意节点自动恢复仍未开放。
- **Go 技术**：序列化、稳定幂等键、故障注入、进程重启恢复。
- **技术（核心，面试高频）**：**Human-in-the-Loop、长任务中断与恢复、检查点**。
- **写代码**：HumanGate 节点调 Eino Interrupt，状态落 PG checkpoint 并释放执行资源；approve/instruct/inline_edit 带版本 resume；版本不符作废。业务产物用稳定操作键幂等提交，重试 attempt 只记调用日志，不改变业务幂等键；恢复时先查询已提交结果再决定是否重执行。
- **创作上**：跑到关键处自动停下等作者批/批注/直接改；进程重启后能从"等审核"原地继续。
- **学会的标志**：能演示"杀掉服务→重启→从 checkpoint 恢复等待中的 run"；旧 draftVersion 的审批被拒；注入“产物已提交但 checkpoint 未保存”故障，重启后不重复写产物、不重复递增版本。模型响应未落库时不能保证不重复调用，须记录结果未知并受重试预算约束。
- **能讲的一句**："人审我用中断-检查点实现，暂停时不占执行资源，恢复时校验版本，迟到的 agent 结果盖不了人的新修改。"

### I8 · 事件、outbox 与 SSE ⭐可观测/流式
- **Go 技术**：流式 HTTP、Flush、连接取消、有界 channel 与背压。
- **技术（核心）**：**执行流事件化、可靠事件（outbox 模式）、流式推送、断线重放**。
- **写代码**：`run_event` 只追加表，业务写入与事件同事务；dispatcher + SSE hub；支持 `Last-Event-ID` 回放与消费端去重；扩展 I3 的 REST。为慢客户端设有界缓冲，溢出时断开并允许按游标重连，不能阻塞编排。
- **创作上**：前端底部 React Flow 实时高亮当前节点、回退边动画、Findings 逐条冒出；刷新/断网能补齐。
- **学会的标志**：curl 能看一章实时推进；断连后在事件保留范围内补齐已持久化事件；重复帧不重复更新 UI，回放切换实时订阅无缺口；游标过期则要求重取快照。
- **能讲的一句**："业务与事件记录同事务，投递失败可重试；SSE 允许重复传输，消费端按 ID 去重并通过回放恢复一致状态。"

### I9 · 完善上下文清单与定稿冻结 → M1 收口
- **Go 技术**：版本引用集合、事务提交与集成测试。
- **技术（核心）**：**上下文工程入门、版本一致性、事务性提交**。
- **写代码**：assembler 注入"本章 beat + 活跃人物卡 + 硬规则 + 上章结尾"，产出 `ContextManifest`（用了什么、来源版本、token 估计、未纳入什么）；沿用 I1/I5 的上下文与版本契约，不在此时重做输入模型；`commit` 单事务冻结已通过当前版本评审的正文与匹配的 Bible/大纲版本，提交前再次校验人工审批及事实候选。
- **创作上**：写作前明确"这一章让模型看到什么"；定稿后未确认事实不会泄露给下一章。
- **学会的标志**：单章从启动到定稿端到端跑通；能解释为什么不能"每次从库里捞最新值拼上下文"。
- **能讲的一句**："每次 run 我冻结输入版本并出一份上下文清单，既保证可追溯，也避免模型读到半个正在改的状态。"

**M1 结束时你拥有的能力**（也是完整面试故事）：图编排、结构化输出、多专家评审、反思返工、护栏、HITL、持久化恢复、可观测流式、上下文装配——一条真实可跑、可中断、可恢复、能被前端实时观察的单章流水线。

## 7. 测试与 LLM 策略（贯穿全程）

- **测试金字塔**
  - domain 纯规则：最多最快，无 IO（聚合、分级、冲突分类、版本冻结、可见性）。
  - 图/节点测试：FakeChatModel 脚本驱动，覆盖正常与全部异常分支。
  - 仓储集成：I6 使用显式指定的本机独立 PostgreSQL 测试库；CI 可用 testcontainers，I10 再加入 pgvector。
  - 端到端：一章 happy path + 等待审核恢复 + 产物提交/checkpoint 间崩溃恢复 + 版本竞争 + 并行 Critic 部分失败 + SSE 重放去重。
- **真实模型用"录制/手动"模式**：开发机对少量固定种子手动跑，响应与 usage 存成 fixture 回放；CI 全离线。
- **每次动 prompt/节点/工具**：跑回归集，防"改好 A 崩坏 B"；eval 结果随代码提交。

## 8. 明确不要早做

- 不要先建完所有表/CRUD/admin 再写 Agent；
- 不要在没有失败用例时凭感觉加节点、堆 Agent 数量、上自主群聊；
- 不要脱离 eval 反复手搓 prompt 求神；
- 不要一上来就微服务、Kafka、Neo4j、多模型网关、多租户；
- 不要让 Eino 节点里直接写 SQL 或塞业务规则（节点保持薄）。
